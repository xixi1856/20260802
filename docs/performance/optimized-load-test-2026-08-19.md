# 第二轮优化压测报告（2026-08-19）

## 结论

本轮按初步报告的优先级实施了 PostgreSQL JIT 关闭、附近查询短缓存、球面距离快速计算、轨迹批量写入和压测认证隔离。最重要的改善是：原先会让所有接口排队 14–18 秒并丢弃 188 次迭代的 19 RPS 混合场景，现在 1144 次业务调用全部成功且零丢弃；轨迹和上报 p95 分别降到 29.64 ms 和 51.78 ms。

附近查询的无缓存随机坐标容量也有明显提升，但高密度热点下仍会在约 35–40 RPS 后持续排队；路线风险在混合负载下 p95 仍为 2.70 s，是当前首要瓶颈。热点重复查询借助 3 秒缓存可以承载约 150–200 RPS，p95 为 40–65 ms，但本机调度和缓存重算尖峰仍造成约 0.5% 的迭代丢弃，不能直接当作生产安全容量。

## 实施内容

- 为 Hikari 新连接执行 `SET jit = off`，避免短空间查询触发高成本 PostgreSQL JIT 编译。
- 附近查询的 `ST_DWithin`/`ST_Distance` 使用球面计算；500 米城市范围的精度损失很小，实测单 SQL 约快 34%。
- 使用 Caffeine 为完整查询参数建立最多 2000 项、3 秒 TTL 的本机缓存，并用 `sync=true` 合并同一热点并发重算。
- 创建、核验和状态流转成功后清空附近缓存；真实 API 验证聚合 `reportCount` 从 1 更新到 2 后可立即读到新值。
- 每批轨迹点由逐点 INSERT 改为一条 MyBatis multi-values INSERT，保留 `(trip_id, recorded_at)` 冲突幂等。
- k6 arrival-rate 场景改为 setup 阶段顺序登录 50 个用户，业务阶段复用 token，避免 BCrypt 登录风暴污染容量结论。
- 修复容器镜像工作流引用不存在的 `aquasecurity/trivy-action@0.30.0`，改为有效的 `v0.36.0`，并更新相关 Action 主版本。

## 测试环境与口径

沿用第一轮同一台 Windows 开发机、同一 Docker 数据卷和 10 万级空间数据。k6 与全部服务同机运行，因此结果只用于回归和瓶颈定位。`load/data/` 与 `load/results/` 保存本地虚拟账号、设备凭据和原始 JSON，均被 Git 忽略，不会推送到仓库。

业务端点延迟使用 `endpoint:*` 标签，排除 setup 登录；setup 约需 15–20 秒，因此 k6 显示的整次运行吞吐不能直接替代场景设定 RPS。随机坐标测试几乎不命中完整参数缓存，热点测试固定同一查询参数。

- 轨迹复测前后行数准确增加 24020，和 1201 批 × 20 点一致。
- 缓存失效通过真实登录、两次查询、聚合上报和立即复查验证，写后立即可见。
- Maven 31 个测试全部通过（含真实 PostGIS 容器和 V1→V3 Flyway 迁移），应用及 PostgreSQL、Redis、MinIO、EMQX、Prometheus、Loki 容器保持运行。

## 当前瓶颈

1. **路线风险空间计算。** 20 点路线、30 米走廊仍产生约 5600 个精确候选；空闲时单 SQL 约 0.22 秒，和附近查询并发后 p95 放大到 2.70 秒。尝试把距离物化为 CTE 没有收益，因此未提交该实验改动。
2. **随机附近查询候选过大。** 500 米高密度热点仍需过滤和排序数万候选，短 TTL 完整参数缓存对随机 GPS 坐标命中率有限。
3. **共享连接池仍会形成读写干扰。** 本轮已大幅缩短占用时间，但路线风险高峰仍能把附近查询 p95 推到 471 ms；直接扩大 10 个连接可能只会增加数据库 CPU 争抢。
4. **缓存是单实例且存在重算尖峰。** Caffeine 不跨实例共享，3 秒过期时首次请求仍需执行完整 SQL；200 RPS 本机测试有 33 次调度丢弃。
5. **MQTT 同步消费模型未在本轮改造。** 第一轮已证明约 100 msg/s 稳定、200 msg/s 会丢消息，此风险保持不变。

## 下一步改进建议

1. 为附近 Feed 和路线走廊建立 H3/geohash 瓦片或定时物化风险摘要，先把候选缩到可控数量，再做精确距离与排序；以原 PostGIS 查询作为权威回退。
2. 将路线/附近只读查询放入独立小连接池或只读副本，并增加并发 bulkhead、最大半径和 statement timeout，保护轨迹与上报事务。
3. 缓存键按 10–30 米网格归一化而非原始浮点坐标；多实例部署时迁移到 Redis，并使用版本号或事件失效避免全量清空。
4. 路线风险对长折线先 `ST_Simplify`/分段取瓦片候选，限制点数与总长度；保存压测下的候选数、数据库 CPU 和连接等待指标。
5. MQTT 回调改为只校验并写有界队列，由固定 worker 批量入库；在改造前把生产发布速率限制在已验证范围内。
6. 在独立压测机进行 5–10 分钟峰值、30–60 分钟 soak、缓存冷启动和故障恢复测试。上线门槛继续要求错误率 < 0.1%、业务场景零丢弃，并同时检查数据库 CPU、连接等待和消息积压。
