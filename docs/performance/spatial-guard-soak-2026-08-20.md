# 空间查询保护与稳态压测报告（2026-08-20）

## 1. 摘要

本轮按既定前五项优化顺序完成：45/50/60 RPS 单机拐点短测、100～500 点路线优化、30/38 RPS 长稳态验证、监控补全，以及空间查询并发限制、SQL 超时和读写保护。

核心结论如下：

- 100～500 点路线先做 5 米保拓扑简化，再按最长 75 米分段生成候选；最终仍对原始路线执行精确距离过滤。500 点、5 RPS 专测 p95 从上一轮的 695.79 ms 降到 194.45 ms，下降约 72.1%。
- 路线加入 5 秒、最多 1,000 条的本地短缓存；100 点同一路线 50 RPS 热点测试完成 1,501 次、零错误、零丢弃，route p95 为 4.78 ms。
- 空间查询统一经过公平信号量，最多 5 个并发，等待 50 ms；nearby SQL 超时 1 秒，route SQL 超时 1.5 秒。Hikari 连接等待上限缩短到 1 秒，防止线程长期堆积。
- 并发上限 6 在 50 RPS 下仍会形成连接排队和数据库 CPU 雪崩；收紧到 5 后，同档整体失败率从约 32.9% 降到 7.16%，Hikari pending 峰值从 6 降到 0，轨迹写入 p95 从 121.84 ms 降到 36.65 ms，上报 p95 从 1,689.30 ms 降到 342.91 ms。
- 30 RPS 与 38 RPS 均完成 30 分钟稳态测试，均为零 dropped、写接口零失败、Hikari pending 全程为 0。整体失败率分别为 0.31% 和 0.52%，全部由空间查询保护产生，满足当前 `<1%` 测试门槛。
- 当前单机可确认的稳态上沿为 38 RPS，但这是“少量 429、写链路保持可用”的工作点，不是零拒绝容量。按约 20% 余量，生产前暂以 30 RPS 作为保守单机总入口工作点更合理。

## 2. 环境、数据与判定标准

### 2.1 环境

- 应用：单个 Spring Boot 容器；Hikari 最大 10、最小空闲 2、连接获取超时 1 秒。
- 数据库：单个 `postgis/postgis:18-3.6` 容器；应用连接关闭 JIT。
- 主机：Windows Docker Desktop，16 个逻辑 CPU，容器没有单独 CPU 配额。
- 工具：k6 2.0.0、Micrometer/Actuator、`docker stats`、PostgreSQL 统计视图。
- 长测结束后的数据：103,890 条无障碍问题、661,261 个轨迹点、118,816 条问题上报，数据库约 365 MB。

Docker CPU 的 100% 约表示占用一个 CPU 核，只适合同机相对比较。30 RPS 先于 38 RPS 执行，后者面对更大的写入后数据集；严格 A/B 应恢复同一数据库快照后分别测试。

长测把 `JWT_ACCESS_TOKEN_TTL` 临时设为 `PT1H`，避免默认 15 分钟令牌过期污染结果。代码与 Compose 的默认值仍是 `PT15M`。

## 3. 实施内容

### 3.1 长路线候选优化

20 点及以下路线继续使用原始分段。超过 20 点时：

1. 使用 `ST_SimplifyPreserveTopology` 做 5 米保拓扑简化；
2. 使用 `ST_Segmentize` 将候选路线控制在最长 75 米一段；
3. 候选阶段把走廊临时扩大 5 米，避免简化漏选；
4. 对候选按原始、未简化路线重新计算距离；
5. 用原始走廊做最终过滤、排序和 Top 100。

20、100、500 点各自抽样比较优化前后 Top 100，数量均为 100、顺序 ID 差异均为 0。该校验降低了当前测试路线上的语义回归风险，但仍建议上线前补真实曲折路线、折返路线和跨城区长路线样本。

### 3.2 短缓存

- nearby：最多 2,000 条、TTL 3 秒；
- route：最多 1,000 条、TTL 5 秒；
- 两者都启用同步回源，避免热点键同时失效时击穿数据库；
- 问题创建、核验和状态变更时同时清空 nearby 与 route 缓存。

混合压测路线使用 3,571 长度的确定性坐标序列，路线专测默认使用 1,009 个变体，避免固定请求把数据库测试变成纯缓存测试。热点缓存另用 `ROUTE_VARIANTS=1` 单独验证。

### 3.3 空间查询舱壁和超时

- nearby 与 route 共享一个公平信号量，默认 `SPATIAL_MAX_CONCURRENT=5`；
- 获取许可最多等待 50 ms，失败返回 `429 SPATIAL_QUERY_BUSY`；
- nearby 的事务内 `statement_timeout=1s`，route 为 `1.5s`；
- SQL 超时转换为 `503 SPATIAL_QUERY_TIMEOUT`；
- Hikari 连接获取与校验超时均为 1 秒；
- Micrometer 增加 active、waiting、rejected、timeout 和按查询类型计时指标。

这是同一连接池上的逻辑 bulkhead，不是物理读写池。它能给写事务保留连接和 CPU 余量，但无法提供只读副本级别的资源隔离。

### 3.4 监控补全

压测采样 CSV 新增：

- 空间查询 active、waiting、rejected、timeouts；
- PostgreSQL 活跃/等待会话和最长查询；
- 定时/请求型 checkpoint、写入和同步耗时、写缓冲数；
- commit、rollback、块读/命中、临时文件、死锁；
- autovacuum、autoanalyze 和死元组；
- 原有 Hikari、后端/数据库 CPU 与内存。

计数器必须使用每轮首尾差值，不能直接把 Prometheus 或 PostgreSQL 累计值当成本轮次数。

## 5. 短时容量与保护调参

| 场景 | 请求 / 失败 / 丢弃 | nearby p95 | route p95 | track p95 | report p95 | Hikari pending 峰值 | 判定 |
|---|---:|---:|---:|---:|---:|---:|---|
| 45 RPS，保护前 | 8,074 / 0 / 29 | 608.64 ms | 756.96 ms | 375.26 ms | 182.93 ms | 6 | 不通过，工具已无法维持到达率 |
| 45 RPS，并发 6 | 8,104 / 204 / 0 | 280.63 ms | 375.27 ms | 31.90 ms | 319.49 ms | 0 | 2.52% 主动拒绝，过载可控但不满足错误率 |
| 50 RPS，并发 6 | 8,996 / 2,960 / 6 | 380.36 ms | 492.10 ms | 121.84 ms | 1,689.30 ms | 6 | 再次雪崩，并发 6 过高 |
| 50 RPS，并发 5 | 9,003 / 645 / 0 | 277.58 ms | 365.92 ms | 36.65 ms | 342.91 ms | 0 | 写链路恢复，7.16% 主动拒绝 |
| 60 RPS，并发 5 | 10,803 / 484 / 0 | 223.18 ms | 274.24 ms | 16.19 ms | 268.08 ms | 0 | 写链路稳定，4.48% 主动拒绝 |

60 RPS 单次短测优于 50 RPS，可能受数据库缓存、请求相位和运行顺序影响，不能解释成负载越高越快，也不能据此把 60 RPS 当容量。两档都超过 1% 错误门槛，只能证明舱壁能把失败限制在空间读接口，不再把写接口和连接池一起拖垮。

并发从 6 降到 5 后吞吐反而提高，说明 6 个重空间查询已经让 PostgreSQL 进入竞争放大区。继续扩大 Hikari 连接池大概率只会增加 CPU 争抢。

## 7. 当前瓶颈与容量解释

1. **nearby 精确候选与距离计算仍是首要成本。** 本轮没有用 H3 替代 PostGIS；应用层保护只控制并发，没有减少单次 nearby 的候选数量。
2. **PostgreSQL CPU 是共享瓶颈。** 并发 6 到 5 的反直觉改善说明数据库已经处于竞争拐点。单纯增加应用节点或连接池不会线性增加容量。
3. **读写仍共享一个物理连接池和数据库。** 当前信号量能保护写入，但 429 是用户可见失败；需要更强隔离时应验证独立读池/写池，数据库成为明确瓶颈后再评估只读空间副本。
4. **38 RPS 不是零拒绝承诺。** 它在当前 `<1%` 门槛下通过，但 30 分钟仍有 0.52% 请求被拒。需要零 429 时，应继续在相同快照上测试 24～30 RPS，或增加队列/预计算能力。
5. **缓存只适合短时热点。** 固定热点路线的性能很好，但随机路线仍必须回源。不能用热点缓存结果代替数据库容量结果。

## 8. 后续建议

1. 在同一数据库快照上补 32/34/36 RPS 各 10～15 分钟，收窄严格容量边界，并至少重复三次报告中位数和离散范围。
2. 为 nearby 持续记录粗候选、精确候选和 Top-K 截止层数量，结合 `EXPLAIN (ANALYZE, BUFFERS)` 定位最坏坐标；证明确实需要时再引入 H3 风险瓦片摘要或 Redis 热点缓存。
3. 验证独立 spatial-read/write 连接池或独立读服务的资源隔离。即使仍连接同一数据库，也应先确认它能否进一步保护写入，不能假定总吞吐会翻倍。
4. 为 429 客户端实现带随机抖动的指数退避，并限制重试次数；禁止立即无间隔重试。
5. 增加缓存命中率、429 比例、SQL 超时、Hikari pending、数据库 CPU、最长查询和死元组告警；长期生产环境补 `pg_stat_statements`。
6. 用真实 3 公里步行路线补 20/100/500 点、直线/弯曲/折返组合，并在独立压测机上重复 60 分钟 soak 和故障恢复测试。
