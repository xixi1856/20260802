# 初步压测报告（2026-08-17）

## 结论

当前后端的普通健康检查和轨迹批量写入表现正常；高密度区域的“附近障碍”和路线风险空间查询是主要瓶颈。慢空间查询会占满 10 个 Hikari 连接，使轨迹、上报等原本很快的接口一起排队。MQTT 同步单消费者链路可稳定处理约 100 条/秒，但 200 条/秒会填满 EMQX 订阅队列并丢消息。

本轮发现并修复了并发聚合映射、MQTT 重连、PostgreSQL 18 参数推断、回调异常隔离和 Prometheus 401 等问题。最终应用健康状态为 `UP`，Prometheus target 为 `up`，Maven 30 个测试全部通过。

## 环境与数据

- Windows 11，AMD Ryzen 7 5800H，8 核 16 线程，宿主机约 13.9 GiB 内存。
- Docker 可用 16 CPU、约 6.7 GiB 内存；k6 v2.0.0 与容器运行在同一台机器。
- 后端 OpenJDK 21.0.11；PostgreSQL 18.6 + PostGIS；数据库测试结束时约 125 MB。
- 初始数据：50 个虚拟用户、50 个虚拟设备、50 个进行中行程、100,000 条障碍和 100,000 条报告。
- 障碍数据 70% 集中在北京热点附近，30% 分布在较大范围。这是确定性、隐私安全的极端热点模型，并非真实城市密度。
- 测试结束数据库一致性：100,100 条障碍、100,702 条报告、26,520 个轨迹点、8,973 条 MQTT 收件箱及路径观察，MQTT 拒绝数为 0。

高档测试期间的实际消费速率约为 145 msg/s，随后 EMQX 为后端订阅者维护的 1,000 条消息队列被填满。结论是当前安全下界至少为 100 msg/s，但 200 msg/s 不可用；增加 broker 队列只能延迟失败，不能解决同步单消费者吞吐。

测试使用虚拟设备和生成数据即可覆盖认证、协议、数据库与聚合逻辑。真实树莓派/摄像头不应作为初期后端压测的前置条件；上线前仍需少量真机做 TLS、弱网重连、时钟漂移、离线缓存和固件行为验证。

## 瓶颈证据

### 1. 高密度空间查询

热点中心 500 米查询中，GiST 索引先返回 69,831 个候选，精确过滤后仍有 54,405 行。为了按 `risk_score`、距离和时间排序，数据库必须计算并排序全部候选，最后才取 20 行。执行计划使用 GiST 和 top-N heapsort，因此“缺索引”不是完整原因，根因是候选集过大且排序字段是运行时表达式。

单条 `EXPLAIN ANALYZE`：

- 默认 JIT：执行 1,819.70 ms，其中 JIT 约 889.03 ms。
- 当前会话 `SET jit=off`：执行 187.13 ms，约快 9.7 倍。
- 缓冲区命中约 4,166 页；优化器估计返回 10 行，实际为 54,405 行，基数估计严重偏低。

阶梯压测时 PostgreSQL CPU 曾接近 1,000%，10 个应用连接全部活跃，实际业务吞吐约 16.9 请求/秒，与“连接池大小 ÷ 慢查询耗时”的量级一致。单纯扩大连接池很可能进一步争抢 CPU。

### 2. 连接池隔离不足

附近和路线查询与轨迹、上报共用 maximum-pool-size=10 的连接池。混合测试中，慢读查询占住连接后，轨迹 p95 从单测的 20 ms 上升到 14.30 s，说明主要时间花在等待资源，而不是轨迹 SQL 本身。

### 3. MQTT 同步消费

Paho `messageArrived` 当前同步完成 JSON 校验、设备查询、轨迹匹配和多次数据库写入。单回调线程无法吸收 200 msg/s，broker 端最终丢消息。压测前还存在重连回调同步等待订阅完成、SQL 参数类型推断失败会终止回调线程等问题，本轮已修复，但处理模型仍需异步化。

### 4. 热点并发聚合

同一位置上报使用 3×3 空间桶的 PostgreSQL 事务 advisory lock，保证聚合正确，但同一热点会串行化。20 RPS 下中位数仅 15.9 ms，尾延迟却达到 p95 650 ms，符合锁等待特征。

## 本轮实施内容

- 修正 PostgreSQL 18 volume 挂载、Flyway starter、TraceId Filter 重复注册和 UUID 类型处理，完整启动 Docker 栈。
- 新增可重复的数据准备脚本、10 万空间数据 SQL、4 个业务 k6 脚本及公共 JWT 登录模块。
- 将聚合 advisory-lock Mapper 从无返回值改为可映射布尔值，修复并发上报 500。
- 修正轨迹和感知 SQL 在 PostgreSQL 18 下的时间、nullable double 参数类型推断。
- MQTT 重连改为非阻塞重新订阅；回调增加异常边界，避免单条消息终止连接。
- 新增 50 设备并发 MQTT 模拟器；Prometheus 指标端点已允许抓取，target 从 401/down 恢复为 up。
- 修正压测轨迹时间生成，确保请求落在服务允许的时间窗口内。

## 改进建议及顺序

1. **先关闭应用 OLTP 连接的 PostgreSQL JIT并复测。** 可用 Hikari `connection-init-sql: SET jit = off` 做灰度。单查询实验收益约 9.7 倍，但必须重新跑阶梯和混合场景确认整体收益。
2. **缩小空间查询候选集。** 为附近结果建立 H3/geohash 网格或物化瓦片，Redis 缓存热点格子 1–5 秒；或先按 KNN/网格取有限候选再计算风险排序。若改变“全半径内风险优先”的语义，需要产品确认。
3. **修正统计信息并设置保护。** 提高 location 列 statistics target、ANALYZE 后验证估计；为空间接口设置 statement timeout、并发 bulkhead 和最大半径，避免慢查询耗尽全池。
4. **隔离读写资源。** 空间读使用独立连接池或只读副本，轨迹/上报保留事务池。不要在数据库 CPU 已满时先盲目扩大 10 连接上限。
5. **异步化 MQTT。** 回调只做最小校验并写入有界队列/消息流，由固定 worker 批量落 `mqtt_inbox` 和业务表；监控队列深度、消费延迟、EMQX dropped 和重连次数。设备侧同时加入抖动、限速和离线重放。
6. **优化批量轨迹。** 当前每批 20 点仍循环执行 20 次 INSERT；容量提高后可改成 MyBatis multi-values、JDBC batch 或 PostgreSQL `unnest`，减少往返。
7. **优化热点锁。** 保持幂等与唯一性前提下，评估更细空间桶、先写报告再异步聚合，降低同一位置 advisory lock 的尾延迟。
8. **做第二轮生产化测试。** 在独立压测机上运行，分别做容量阶梯、5–10 分钟峰值、30–60 分钟 soak、故障恢复和少量真机弱网测试；以 p95/p99、错误率、丢弃数、连接池等待、数据库 CPU 和消息积压共同判定。

## 初步验收门槛建议

- 普通查询/写入：错误率 < 0.1%，p95 < 300 ms，p99 < 800 ms，`dropped_iterations=0`。
- 关键上报：错误率 < 0.1%，p95 < 500 ms，且数据库聚合计数完全一致。
- MQTT：业务表落库数必须等于唯一发布事件数，拒绝和 broker dropped 为 0，持续积压能在约定时间内清空。
- 任何接口不能因空间查询压力导致跨接口 p95 上升到秒级。

以上是单机开发环境的初步基线，只适合定位问题和后续回归，不应直接换算生产并发用户数。
