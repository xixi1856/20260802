# 路线风险第三轮优化压测报告（2026-08-19）

后续 nearby 分阶段诊断、优化及 21～38 RPS 复测见
[附近查询分阶段诊断、优化与复测报告](phased-nearby-optimization-2026-08-19.md)。

## 结论

本轮把路线风险的默认走廊从 30 米调整为更符合步行场景的 20 米，并将整条 LineString 一次粗过滤改为逐线段走 GiST 索引、候选去重、全路线距离只计算一次。相同 20 米、10 RPS 路线专测从 230 完成/71 丢弃、p95 24.86 秒，改善为 300 完成/0 丢弃、p95 193.90 ms；20 RPS 加压同样零丢弃，p95 162.40 ms。

原 19 RPS 混合场景全部门槛通过，路线 p95 从第二轮的 2.70 秒下降到 196.64 ms。27 RPS 中间档零错误、零丢弃，但附近查询 p95 314.03 ms，略高于 300 ms 目标；38 RPS 已出现 49 次丢弃和跨接口排队。因此当前单机严格 SLA 工作点仍建议 19 RPS，27 RPS 可视为临界区，38 RPS 不可用。

## 为什么分段过滤有效

原 SQL 使用整条约 1.3 公里的斜线做一次 GiST 包围盒过滤。斜线的包围矩形覆盖大量并不靠近路线的热点数据，索引先返回约 4.9 万条粗候选，再对每条候选计算到完整折线的距离。

新 SQL 使用 `ST_DumpSegments` 拆出各线段，每段分别执行 `ST_DWithin`。每段的包围盒更窄，数据库只对真正靠近局部线段的数据做精确判断；随后按 Issue ID 去重，并对去重后的候选计算一次到完整路线的距离。该方式保留最终业务排序语义。

20 米走廊的对照查询结果：

- 旧查询精确候选：3727。
- 新查询精确候选：3727。
- 两种查询最终 Top 100：ID 差异为 0。
- 同机空闲 SQL 对比：整线过滤约 190–228 ms，分段过滤约 113–138 ms。

30 米走廊约有 5601 个精确候选；改为 20 米后约 3727 个，减少约 33.5%。这部分收益来自业务范围收窄，分段过滤的收益来自减少索引假阳性和重复距离计算，两者需要分开理解。

## 实施内容

- 路线默认 `corridorMeters` 从 30 改为 20；API 仍允许客户端明确传入 5–100 米。
- OpenAPI 默认值同步为 20，业务混合脚本支持 `ROUTE_CORRIDOR_METERS`。
- 路线 SQL 增加 `route`、`segments`、`candidate_ids`、`distances` 四阶段 CTE。
- `ST_DWithin` 和 `ST_Distance` 使用球面快速计算，与附近查询口径一致。
- 新增 `k6-route-risk.js`，使用轻微平移的 20 点路线，避免把固定参数缓存当成数据库容量。
- 单元测试覆盖 20 米默认值和客户端显式传入 30 米的兼容行为。

38 RPS 虽然没有 HTTP 错误，但空间查询再次造成数据库 CPU/连接争用，上报接口出现长时间等待。错误率为零不代表该档位可用。

## 当前瓶颈和下一步

1. 随机附近查询重新成为首要瓶颈。27 RPS 时它是唯一超过 p95 目标的接口，38 RPS 时首先形成排队。
2. 读写仍共用 10 个 Hikari 连接。高空间读压力会把事务写接口拖慢，需要读写连接池 bulkhead 或只读副本。
3. 分段 SQL 对输入点很多的路线会增加索引探测次数。上线前需补 100/500 点、不同路线长度和弯曲程度的测试，并考虑按固定长度合并或简化线段。
4. 球面快速距离在城市短距离场景应继续用真实坐标抽样验证；需要测绘级精度的功能仍应使用椭球距离。
5. 下一轮优先为附近查询增加 H3/geohash 候选分桶或风险瓦片摘要，并保留 PostGIS 精确距离作为最终校验。
