# 附近查询分阶段诊断、优化与复测报告（2026-08-19）

后续路线长点数、空间查询保护及 30 分钟稳态复测见
[空间查询保护与稳态压测报告](spatial-guard-soak-2026-08-20.md)。

## 1. 摘要

本轮按“诊断基线、确定容量、依据证据优化、同条件复测”的顺序完成。测试数据为约 10 万条有效无障碍问题，附近接口使用 500 米半径、Top 20，路线接口使用约 1.3 公里路线和 20 米走廊。所有容量档均运行 3 分钟，测试前单独预热 60 秒；k6 的 50 用户登录阶段不计入业务资源统计。

结论如下：

- 旧 nearby SQL 在中心热点先取得约 6.99 万条包围盒候选，精确过滤后仍有约 5.44 万条，并为这些行计算距离。单 SQL 热缓存执行时间约 110～126 ms。
- 21 RPS 基线可满足 SLA；23 RPS 的 nearby p95 已为 339.15 ms，超过 300 ms；25 RPS 出现暂态雪崩，27 RPS 虽无丢弃但 nearby p95 为 726.89 ms。因此旧实现的严格 SLA 工作点只能确认到 21 RPS。
- 优化利用“风险分数是第一排序键”的业务语义，以部分表达式索引从最高风险层向下累计到 Top 20 所需的截止层，只对截止层以上记录计算距离。中心 SQL 约降到 24.21 ms，执行时间降低约 80.8%。
- 六个不同坐标的新旧 Top 20 顺序逐项比较，ID 差异均为 0。
- 优化后 21、23、25、27 RPS 全部通过；追加的 38 RPS 档也运行 3 分钟并全部通过，nearby p95 为 192.96 ms、零错误、零丢弃、Hikari pending 峰值为 0。
- 当前只能确认严格 SLA 容量下界至少为 38 RPS，尚未测出新上限。按 20%～25% 容量余量，当前数据和本机环境可暂以约 28～30 RPS 作为保守工作点，不应把 38 RPS 直接当生产配置。
- 500 点路线在 5 RPS 下 p95 为 695.79 ms，仍低于 800 ms，但明显接近门槛。长路线点数已成为下一项优先风险。

## 2. 环境、数据和判定标准

### 2.1 环境

- 应用：单个 Spring Boot 容器，Hikari `maximum-pool-size=10`、`minimum-idle=2`。
- 数据库：单个 `postgis/postgis:18-3.6` 容器，JIT 在应用连接中关闭。
- 主机：Windows Docker Desktop，共 16 个逻辑 CPU；容器没有单独 CPU 配额。
- 数据：约 100,000 条种子问题，测试写入后有效问题约 100,000～101,000 条。
- 工具：k6 2.0.0、Spring Boot Actuator/Micrometer、`docker stats`、PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`。

Docker CPU 的 100% 表示约占用一个 CPU 核。采样命令本身有少量开销，因此 CPU 数值适合用于同机相对比较，不应外推为生产硬件容量。

### 2.2 SLA

| 端点 | p95 目标 |
|---|---:|
| 附近问题 | < 300 ms |
| 路线风险 | < 800 ms |
| 轨迹批量写入 | < 500 ms |
| 问题上报 | < 500 ms |

共同条件为 HTTP 错误率低于 1%、检查成功率高于 99%、`dropped_iterations=0`。容量结论还要求不能出现持续连接排队或跨接口雪崩。

### 2.3 可复现性调整

原混合脚本使用 `Math.random()` 生成坐标，前后两轮无法严格复现。本轮改为基于场景迭代号的确定性序列，相同档位会依次访问相同坐标。新增 `run-profiled-business-mix.ps1` 同时保存：

- `load/results/<name>.json`：k6 汇总；
- `load/results/<name>-metrics.csv`：Hikari、后端和 PostgreSQL 容器采样；
- `load/results/<name>.stdout.log` / `.stderr.log`：k6 日志。

这些文件包含本机运行信息并且数量较大，继续由 `.gitignore` 排除；仓库只保存脚本和本报告中的汇总。

## 3. 第一阶段：nearby 基线诊断

### 3.1 候选规模

使用压测脚本前 20 个确定性坐标统计 500 米范围候选：

| 指标 | 最小 | 平均 | 最大 |
|---|---:|---:|---:|
| GiST 包围盒候选 | 27,367 | 48,229 | 69,875 |
| `ST_DWithin` 精确候选 | 14,738 | 34,244 | 54,445 |

中心点 `(116.397128, 39.916527)` 单独统计约有 69,952 个包围盒候选、54,449 个精确候选。候选规模随坐标变化很大，随机附近查询不能只用一个固定热点代表。

### 3.2 SQL 执行计划

旧 SQL 使用 `idx_issue_location_gist` 做 Bitmap Index Scan，再执行 Parallel Bitmap Heap Scan。中心点的主要计划数据为：

- GiST 返回约 69,957 行；
- 精确过滤后输出约 54,449 行；
- 全部输出行计算 `ST_Distance`；
- Top-N heapsort 最终只保留 20 行；
- shared buffer hit 约 4,195；
- Execution Time 约 110.11 ms，重复计划样本约 125.87 ms。

排序本身只使用约 27 KB，主要成本不是排序内存，而是为数万候选执行精确空间判断和距离计算。

### 3.3 指标解释

23 RPS 时 Hikari pending 峰值仍为 0、连接获取平均约 0.12 ms，但连接平均占用和 PostgreSQL CPU 已上升，说明 SLA 首次超标发生在 SQL 服务时间阶段。25/27 RPS 进入非线性区后，Hikari 才出现排队并把写接口一起拖慢。

因此本轮没有先做读写双连接池，也没有直接引入 H3。双池只能隔离故障，不能降低同一数据库的 CPU；行级 H3 分桶也不能保证减少 500 米范围内的真实候选。

## 5. 第三阶段：定向优化

### 5.1 利用排序语义减少距离计算

nearby 的排序为：

1. `risk_score DESC`；
2. `distance_meters`；
3. `last_reported_at DESC`。

`severity` 被数据库约束为 1～5，`confidence_score` 被约束为 0～100，因此 `risk_score = severity * confidence_score / 10` 的最大整数值固定为 50。新查询从风险 50 分开始，利用递归 CTE 逐级统计半径内命中数；累计达到请求 `limit` 后确定截止风险层。最终只读取截止层及更高风险的记录，计算距离并保持原排序。

配套的 Flyway V4 创建活动问题部分表达式索引：

```sql
CREATE INDEX idx_issue_active_risk_score
    ON accessibility_issue (((severity * confidence_score / 10)::integer) DESC)
    WHERE status IN ('PENDING', 'VERIFIED', 'PROCESSING');
```

该方案没有预先截断同风险分组；截止风险层中的所有记录仍参与距离排序，所以不会把“同风险更近”的记录漏掉。

### 5.2 SQL 对比

中心热点最高风险 50 分在半径内有约 102 条。新计划先从风险索引检查约 246 条全局 50 分活动记录，再对半径内约 102 条做最终距离排序：

| 指标 | 旧查询 | 新查询 |
|---|---:|---:|
| 最终距离候选 | 约 54,449 | 约 102（截止层以上） |
| shared buffer hit | 约 4,195 | 约 1,169 |
| Execution Time | 约 125.87 ms | 约 24.21 ms |
| 执行时间变化 | - | -80.8% |

新查询在热点数据上明显更有利。稀疏位置可能需要向下检查多个风险层，收益会缩小；本机两个稀疏/空位置的完整 API 调用约为 54.3 ms 和 13.6 ms，仍低于 nearby SLA，但仍需在真实城市边缘数据上继续验证。

容器重启后的第一个中心 API 请求约为 610.6 ms，随后三个未命中应用缓存、但数据库和 JVM 已预热的相邻坐标约为 105.5～151.6 ms。容量表反映的是预热后的稳态能力；如果部署后必须立即承载流量，应在 readiness 放量前增加代表性空间查询预热，或单独设定冷启动 SLA。

### 5.3 正确性验证

选取中心、四个热点边缘和一个较远坐标，用旧 SQL 与新 API 比较 Top 20：

- 每个坐标旧、新结果数均为 20；
- 每个位置按顺序比较的 ID 差异均为 0；
- HTTP 状态均为 200；
- Flyway schema history 已登记 V4。

## 7. 当前瓶颈和风险

1. **新容量上限尚未确定。** 38 RPS 仍通过，只能报告“已验证下界至少 38 RPS”，不能宣称最大容量为 38 RPS。
2. **500 点路线成为明确风险。** 当前 5 RPS 已达到 p95 695.79 ms；若和更高 nearby 压力并发，可能超过 800 ms。
3. **优化依赖风险分布。** 热点中最高风险层已有足够 Top 20 时收益最大；真实数据如果高风险记录稀少，递归需要检查更多风险层。
4. **25 RPS 基线存在未解释暂态。** 需要 PostgreSQL 检查点、自动清理和 `pg_stat_statements` 时间线才能进一步归因。
5. **测试数据仍为合成热点。** 它适合制造空间计算压力，但不能代表所有城市密度、风险分数分布和真实 GPS 误差。
6. **尚未执行长时间 soak。** 三分钟可以确定初步拐点，不能验证内存增长、缓存抖动、自动清理或检查点周期。

## 8. 后续建议和优先级

### P0：先处理长路线输入成本

- 保留原始路线用于最终距离校验，但在候选发现阶段按小于走廊容差的阈值简化或按固定物理长度合并线段。
- 增加“路线长度 × 点数 × 弯曲度”矩阵；本轮只控制了相同长度下的点数变量。
- 在产品层定义合理的采样密度。500 点/1.3 公里约每 2.6 米一个点，通常存在明显冗余。

### P1：找出新容量拐点并做稳态验证

- 继续测试 45、50、60 RPS，找到首次出现 nearby p95 超标或 pending 的档位。
- 对临界档上下各重复 2～3 次，每档至少 5～10 分钟。
- 在建议工作点执行 30～60 分钟 soak，并采集 PostgreSQL checkpoint、autovacuum、temp file 和语句统计。

### P2：增加查询退化监控

- 记录 nearby 每次使用的截止风险分数、递归层数和最终距离候选数。
- 当递归层数持续升高时，重新比较原 GiST 方案或做自适应分支。
- 开启 `pg_stat_statements`，区分 SQL planning、execution 和总 CPU 成本。

### P3：按证据决定资源隔离和 H3

- 38 RPS 下 pending 仍为 0，当前没有立即拆读写连接池的证据。先找到新拐点，再决定应用 bulkhead 或双池大小。
- H3 更适合作为热点缓存键、格子 Top-K 或风险摘要，不建议当前直接替换 PostGIS 权威查询。
- 只有当更高档位再次证明真实候选规模和重复热点是主要成本时，再投入 H3/瓦片物化。
